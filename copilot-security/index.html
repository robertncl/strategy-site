Controlling GitHub Copilot: what gateways, sandboxes and harnesses actually cover

A landscape and threat map for teams running Copilot's agentic surfaces. Between October 2025 and July 2026, working exploits were demonstrated against Copilot Chat, the Copilot cloud agent and its peers — and the controls that vendors ship for them each stop short in a documented, specific place.

Headline takeaways

01

The injection surface is the collaboration surface

Pull request titles, issue bodies and review comments are attacker-writable and agent-readable. The April 2026 “Comment and Control” disclosure confirmed hijacks of Claude Code Security Review, Gemini CLI Action and the GitHub Copilot Agent through exactly those fields, with credentials exfiltrated back through GitHub itself — no attacker server required.6,8

Established — researcher disclosure + CSA note
02

Copilot's firewall is scoped narrower than most teams assume

GitHub's own documentation states the agent firewall applies only to processes the agent starts via its Bash tool — not to MCP servers, not to configured setup steps, and only inside the Actions appliance. It also warns that sophisticated attacks may bypass it.1

Established — vendor documentation
03

Three control planes, three different units of traffic

An LLM gateway governs model calls; an MCP gateway governs tool calls; a sandbox governs syscalls and egress; a harness governs the agent loop. They are not substitutes, and coverage gaps sit at the seams between them — which is where every confirmed 2026 exploit landed.24

Established framing + our inference on the seams
04

Isolation moved off the shared kernel

By February 2026 the practitioner consensus reported across sandbox vendors and researchers was that Docker/runc isolation is not the right default for AI-generated code; microVMs (Firecracker, Kata) and gVisor are.18 GitHub's own answer — local and cloud sandboxes for Copilot CLI — is still public preview.3

Contested — “consensus” asserted by secondary sources
05

Your CVE feed will not warn you

Anthropic, Google and Microsoft each paid a bounty for the Comment and Control findings and shipped limited mitigations. None assigned a CVE or published an advisory, so dependency scanners and CVE-triggered update tooling see nothing.6,9

Established — CSA note, corroborated by trade press
06

Defaults are permissive by design

Org-level firewall settings arrived in April 2026, but all three ship as “Let repositories decide” to preserve existing behaviour — so an untouched organization has not enforced anything.4,1

Established — changelog + documentation

Scope and method

What this report is, and what it is not

The subject is GitHub Copilot — its cloud agent, its CLI, its code review agent and the policy surfaces GitHub exposes around them. Everything else (gateways, sandbox primitives, harness designs, MCP) appears as context for controlling Copilot, not as a market survey in its own right.

Load-bearing claims are taken from primary sources where one exists: vendor documentation, changelog entries, the researchers' own disclosure, and the Cloud Security Alliance research note that reproduces its detail. Where only secondary reporting or a vendor blog exists, the claim is labelled as such and the disagreement is left visible rather than averaged away. Product capability statements were read from vendor documentation on 31 July 2026; agentic tooling changes weekly, so verify anything you intend to rely on as a control.

No architecture is recommended. Section 06 lists what we could not establish.

How the Copilot Agent exploit got through three layers

Of the three agents, Copilot required the most work, because GitHub had already shipped three runtime defences: environment-variable filtering, secret scanning on agent output, and the network firewall. Per the CSA reconstruction of the disclosure, the payload was hidden in an HTML comment — concealed in GitHub's rendered Markdown but read raw by the agent — and each layer was defeated separately: variables were read through an alternative mechanism, the scanner was defeated by encoding the values into a shape its patterns did not match, and the firewall was sidestepped by exfiltrating through GitHub's own API endpoints rather than an external host.6

02
The four control planes

What each layer can see

“Gateway, sandbox, harness” is not a stack in which the outer layer contains the inner one. Each intercepts a different unit of traffic, and a control can only enforce policy on traffic it sees. An LLM gateway's unit is a model call; an MCP gateway's is a tool call; a sandbox's is a syscall and a packet; a harness's is a step in the agent loop.24,21

Model plane
LLM gateway
Sees prompts, completions, tokens, spend. Enforces routing, budgets, redaction, jailbreak filters.
Blind to: what the agent then does locally
Tool plane
MCP gateway
Sees tool invocations. Enforces per-tool RBAC, identity propagation, allowlists, immutable audit.
Blind to: shell commands and file writes
Execution plane
Sandbox
Sees syscalls, filesystem, egress. Enforces the blast radius when generated code runs.
Blind to: intent — a hijacked agent inside a perfect sandbox still acts
Decision plane
Harness
Sees the loop: context assembly, tool exposure, approvals, hooks. The only layer that can refuse before an action exists.
Blind to: anything outside its own process

The “blind to” lines are our reading of each layer's documented scope, not vendor statements.

03
GitHub-native controls
Vendor documentation

What GitHub already gives you

More than most teams have turned on. GitHub documents a substantial set of guardrails for the cloud agent, and the interesting part is not the list but the boundary conditions attached to each item.2

Who can start an agent

Only users with write access can trigger the cloud agent; comments from users without write access are never presented to it. Automations ignore events from non-write users by default.2

What it can write

A single branch, subject to branch protection. It cannot run git push directly, cannot mark its own PR ready for review, and cannot approve or merge. The person who asked for the PR cannot approve it either.2

Workflow execution

Actions workflows do not run on agent PRs until a write-access human clicks “Approve and run workflows” — which also breaks automation-triggers-automation chains. This is optional and can be disabled.2

Traceability

Commits are authored by Copilot with the requesting human as co-author, signed and shown as Verified, and each commit message links to the session log. Session logs and audit-log events are available to administrators.2

Generated-code checks

CodeQL, Advisory Database checks on new dependencies, and secret scanning run by default on the agent's own output, without requiring a GitHub Advanced Security licence — and each can be switched off.2

Injection filtering

GitHub documents filtering hidden characters before user input reaches the agent, giving HTML comments in issues as the example.2 Note the tension with section 01: the April 2026 exploit used precisely a hidden HTML comment.

The agent firewall, and its four documented edges

Internet access is limited by default, with a recommended allowlist covering OS package repositories, container registries, language package registries, certificate authorities and Playwright browser downloads. Blocked requests surface as a warning on the pull request showing the address and the command that tried it.1,5 As of April 2026, organization owners can set Enable firewall, Recommended allowlist and Allow repository custom rules at org level and maintain an org custom allowlist that repositories cannot delete from — and each of those three settings defaults to “Let repositories decide.”4,1

From GitHub's own limitations section
— Applies only to processes the agent starts via its Bash tool. Not MCP servers. Not configured setup steps.
— Operates only inside the GitHub Actions appliance environment.
“Sophisticated attacks may bypass the firewall, potentially allowing unauthorized network access and data exfiltration.”
— Disabling it lets Copilot connect to any host.
Quoted and paraphrased from GitHub Docs, read 31 July 2026.1

Two consequences follow directly, and both are ours rather than GitHub's. First, MCP traffic needs its own control — the firewall will not cover it. Second, because the firewall lives inside the Actions appliance, it is not a substitute for enterprise egress policy on developer machines or self-hosted runners.

MCP: policy exists, per-server granularity is newer

GitHub now documents MCP management, an MCP registry, MCP server access configuration and MCP allowlist enforcement as administrative surfaces, and Visual Studio 2026 reads an allowlist of approved MCP servers configured through Copilot enterprise policy — connections to servers not on the list are blocked in the editor.30,1 Community guidance from the 2025 preview period describes the older situation, when the practical route to “only these servers” was an on/off MCP policy combined with firewall and perimeter egress allowlisting.37 If you are writing policy now, check which of these applies to your plan rather than trusting either account.

Copilot's own sandboxes — useful, and labelled preview

GitHub ships two isolation options for Copilot CLI. Local sandboxing (/sandbox enable) restricts filesystem, network and system capability access on the developer's own machine; it runs on macOS and Linux, with Windows on Insiders builds, and isolation behaviour differs per platform because each OS uses a different backend. Policies can be centrally enforced through Intune or another MDM. Cloud sandboxing (copilot --cloud) runs sessions in isolated ephemeral Linux environments built on Azure Container Apps Sandboxes, with GitHub supplying identity, policy and billing; an org or enterprise owner must enable the Cloud Sandbox access policy, and cloud sandbox policy shares configuration with cloud agent policy. Local sandboxing is included in the seat; cloud sandboxing is metered on compute-seconds, GiB-seconds of memory and GiB-months of snapshot storage.3

The documentation carries a public-preview notice. Independent commentary in July 2026 made the same point in operational terms: usable, but not something to present as a settled compliance boundary without verifying current behaviour for your own OS and CLI build.29

04
AI gateways and MCP gateways

The gateway layer

An AI gateway is a single entry point in front of model providers that reasons in AI-native terms: it budgets and rate-limits by tokens rather than requests, routes across providers, caches semantically similar prompts, and inspects prompts and completions for safety.21 For agent control specifically, the useful properties are the boring ones — a chokepoint where every model call is attributable to a team, capped, logged, and screened.

The Copilot-specific catch

A gateway can only govern traffic you can point at it. With Copilot on GitHub's own model endpoints, the model call is GitHub's to make, not yours to proxy. GitHub does document bring-your-own-key paths — “use your own API keys” at organization and enterprise level, and BYOK model providers for Copilot CLI, the Copilot app and the SDK — which is the documented seam through which model traffic could be routed to a provider endpoint you control.1 Whether that yields gateway-level enforcement for your plan and surfaces is exactly the question to put to GitHub in writing; we could not establish it from public documentation.

Separately, GitHub documents allowlist guidance for Copilot endpoints behind a corporate firewall or proxy, plus subscription-based network routing for attributing Copilot traffic to an enterprise — perimeter controls rather than gateway controls, and explicitly incomplete on their own: allowlisting the Copilot URLs is not enough if the network blocks GitHub more broadly.5

MCP gateways: the tool plane

An MCP gateway proxies between agents and MCP servers, enforcing authentication, per-tool RBAC, allow/deny lists, rate limits on tool invocations and structured audit before a call reaches a downstream system.25 The threats it addresses are protocol-specific and not covered by a generic API gateway: tool poisoning through instructions hidden in tool descriptions, tool redefinition after approval (“rug pull”), and cross-server shadowing where a malicious server impersonates a trusted one.28

Two transport facts matter for policy writing. Per the MCP specification's 2025-11-25 revision, SSE is deprecated in favour of streamable HTTP, and stdio — appropriate for local developer use — provides no network-level authentication to bind a call to an identity, so it should not be the production transport for shared servers; streamable HTTP with OAuth 2.1 and PKCE is the supported remote path.26 The failure mode is not hypothetical: CVE-2026-33032 (CVSS 9.8, May 2026) was an MCP message endpoint that did not authenticate command-execution requests at all.27

Caveat on this subsection: most available MCP-gateway comparisons are published by MCP-gateway vendors. The threat categories are consistent across them and match the OWASP taxonomy; specific product capabilities should be verified independently.

Isolation primitives

Sandboxing, concretely

“Sandboxed” is not one property. A shared-kernel container, a gVisor sandbox and a microVM have materially different security boundaries, and the practitioner and vendor commentary through early 2026 converged on the view that shared-kernel containers are the wrong default for untrusted, model-generated code.18,17 That framing is asserted rather than measured — treat it as the field's prevailing opinion.

What shipped for developer machines

The isolation question moved onto the laptop in January 2026, when Docker Desktop 4.58 began giving each agent its own microVM through the native hypervisor — virtualization.framework on macOS, Hyper-V on Windows — with a private Docker daemon and network isolation, listing Claude Code, Codex, Copilot, Gemini and Kiro among supported agents.19 Anthropic's Claude Code takes a different route, backing its sandboxed bash tool with Seatbelt or bubblewrap plus a network proxy.20 For teams standardising on devcontainers, the same inventory notes the dev-container spec as the common wrapper.20

The limit of this layer is worth stating plainly, because it is where sandbox marketing tends to over-promise: isolation bounds what escapes the environment. It does not bound what a hijacked agent does with the authority it legitimately holds inside that environment. The Comment and Control exfiltration route — the GitHub API the agent is supposed to use — would survive a perfect sandbox.

06
Harness and permissions

The harness is the enforcement point

The harness is the software around the model that assembles context, exposes tools, executes tool calls, manages the agent loop and feeds results back — the layer GitHub described in its May 2026 write-up of the Copilot harness in VS Code, and which it argued in June 2026 is now the unit of competition, with one shared harness behind Copilot CLI, the Copilot app, code review and SDK experiences.32 For security purposes the relevant point is narrower: the harness is the only layer that can decline an action before it exists.

Copilot CLI's permission surface

Trusted directories, tool approvals, path permissions, URL permissions, hooks, secret redaction and sandboxing. The CLI reached GA in February 2026 and ships updates constantly, so flags and behaviour move.29

Hooks beat prompts

A preToolUse hook is your code running at a fixed point in the loop with the final word — the practical enforcement point for rules like “never write to production” or “never push from an agent.” Permission prompts route the decision through the model; hooks do not.29,31 GitHub documents hooks for the cloud agent, the CLI and the SDK.1

Permission modes, as a comparison

Claude Code uses allow/ask/deny rules with six modes (default, acceptEdits, plan, auto, dontAsk, bypassPermissions). Its auto mode, introduced March 2026, routes borderline actions through a background classifier that sees the user request and the tool call but not the main model's prose — a deliberate design against the model talking the gate open.33

Least agency, not just least privilege

OWASP's framing for agentic systems limits not only what an agent can reach but how far it may act without checking back, paired with observability tied to a verified agent identity. Autonomy is earned rather than granted by default.14

Identity and secrets: the CI/CD hardening that actually paid off

The CSA note's recommendations after Comment and Control are unglamorous and specific: audit workflows triggered by pull_request, issues, issue_comment and pull_request_review_comment that pass event content into a model call; remove service API keys from runner environments where they are not strictly required and scope them where they are; restrict GITHUB_TOKEN with an explicit permissions: block, dropping write access for agent steps that only read; pin actions to full commit SHAs; gate agent workflows on team membership or maintainer approval for first-time contributors; scan agent-posted output, not just repository content; and rotate credentials that were exposed to affected agents.6 Independent advisories through 2026 repeat the same pinning and pull_request_target guidance.15

The pattern OWASP-aligned teams push toward — a distinct agent identity rather than a borrowed human session, scoped time-bound revocable permissions, and provable attribution after the fact — is the same conclusion arrived at from the incident side. Most of these failures are authorization problems wearing an AI costume.14

07
Where the evidence is thin

What we could not establish

Quantified sandbox benefit

A claim that sandboxed agents see roughly 90% fewer security incidents circulates attributed to “2026 infrastructure research.”35 We found no primary study, methodology or population behind it. Do not put it in a business case.

MCP adoption figures

Figures such as 78% enterprise MCP adoption and 9,400+ registry servers appear in vendor buyers' guides without methodology.36 Directionally plausible, not citable.

A live contradiction on HTML-comment filtering

GitHub documents that hidden characters, HTML comments included, are filtered before reaching the cloud agent.2 The April 2026 research reports a hidden HTML comment payload working against the Copilot Agent.6 Both may be true at different versions or on different surfaces; the researchers note vendors did not notify users of pinned versions, so version scope is unresolved. We are reporting the disagreement rather than resolving it.

The “RoguePilot” disclosure

A February 2026 Copilot/Codespaces prompt-injection finding attributed to Orca Research, reportedly patched before disclosure on 24 February 2026, reached us only through secondary write-ups.38 We could not read a primary advisory and have deliberately left it out of the incident table.

Whether BYOK gives you real gateway enforcement

GitHub documents bring-your-own-key paths for several Copilot surfaces, but we could not establish from public documentation which surfaces route all model traffic through a customer-controlled endpoint, or whether completions and agent calls behave the same way. This is the single highest-value question to resolve before designing a gateway-centred control.

Exploitation in the wild

A July 2026 advisory describes active exploitation of prompt injection in GitHub agentic workflows while noting the issue is not in the CISA KEV catalogue.15 Absent KEV listing or vendor confirmation, treat “widely reported” as weaker than “confirmed.”
