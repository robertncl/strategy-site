What changed

Agents changed the token math.

A chat assistant answers one prompt and stops. An agent plans, calls tools, reads the results, and loops — re-feeding its whole context on every step. The same task that cost a few thousand tokens as a chat now costs hundreds of thousands as an agent. And agents don't wait for a human to type: they run in CI, on schedules, in fleets.

10–100×tokens per task, agent loop vs. a single chat exchange
1M+tokens burned by one long agentic coding session
24/7background agents don't sleep — volume compounds with adoption

Token appetite grows with success: the better the agents work, the more work we give them. That's the point — and the problem, if every token is metered.

Problem 01 · Economics

Per-token pricing turns success into a cost problem.

  • Frontier list prices: roughly $3–15 per million input tokens and $15–75 per million output — before agentic loops multiply the volume.
  • Linear forever: usage-based pricing means the marginal cost of "thinking" never falls, no matter how much we scale.
  • Not in our control: vendors reprice, deprecate models mid-project, and rate-limit exactly when agents need burst capacity.
  • Illustrative: a 20-developer team with always-on agents can reach ~2B tokens/month — at a blended $8/M that's $16k/month for one team.

The meter is the business model. Our agents are the ones feeding it.

Renting intelligence by the token is rational for scarce, frontier-grade reasoning. It is a terrible deal for the bulk work — refactors, tests, docs, extraction, triage — that makes up most of what agents actually do all day.

Problem 02 · Access risk

Model access is now a supply-chain risk.

The best closed models sit in two jurisdictions that are actively restricting each other. Access can change with a rule, not a market.

United States

Bloc A
  • Export-control regimes already treat advanced chips — and frontier model weights — as controlled technology.
  • Federal moves to bar PRC-developed models from government systems; entity lists can extend to customers and regions.
  • US frontier APIs already block service to a growing list of countries.

China

Bloc B
  • Generative models require regulatory filing before public use; rules can change what domestic operations may run.
  • US providers restrict or geo-block access from China — teams and subsidiaries there can't rely on the same stack.
  • Data-security law limits what can leave the country — closed foreign APIs are a compliance dead end.

If a core workflow depends on one closed API in one jurisdiction, the roadmap depends on two governments staying friendly. That is not an engineering plan.

The common thread

A closed API is a revocable dependency.

  • It can be repriced — and has been, in both directions, on short notice.
  • It can be deprecated — model versions retire on the vendor's schedule, not ours.
  • It can be rate-limited — capacity goes to whoever the vendor prioritizes.
  • It can be geo-blocked — by the vendor's choice or their regulator's order.
  • It sees our data — every prompt crosses a trust boundary we don't control.

Anything we rent can be taken back. Weights we hold cannot.

A downloaded open-weight model is a file. It runs in our tenant, on our GPUs, under our license — indifferent to price changes, deprecation schedules, and export rulings made after the download.

The hedge

Open weights closed the gap — from three blocs at once.

Frontier-class open models now ship from the US, China, and the EU under permissive licenses. Sourcing from all three blocs and running them ourselves is the hedge: no single government can switch our stack off.

The platform · Production tier

Azure AI Foundry: our tenant, our throughput.

Foundry's catalog already carries the open-weight families above — DeepSeek, Qwen, Llama, Mistral, gpt-oss — deployable two ways, behind one endpoint:

Start hereServerless endpoints

Pay-as-you-go per token, zero infrastructure, elastic. Open-weight pricing is a fraction of frontier list price. The on-ramp: prove routing and evals before committing GPU quota.

Scale hereManaged compute

Dedicated GPU capacity in our subscription — reserved, flat-rate, no per-token meter and no shared rate limits. The weights run inside our network boundary; utilization is ours to optimize.

  • Entra ID auth, VNet + Private Link, content-safety filters, observability — the governance we already run on Azure applies to model traffic too.
  • Prompts and outputs stay in our tenant, in the region we choose — nothing transits a model vendor's infrastructure.
  • Model router + versioned deployments: we pin model versions and retire them on our schedule.

The platform · Edge tier

Local hardware: the free inner loop.

Today's workstations run serious models. A 32 GB GPU or a 128 GB unified-memory machine serves 20–120B-class models locally via Ollama, LM Studio, vLLM, or llama.cpp — the same OpenAI-shaped API as everything else.

What runs on a desk

RTX 5090 (32 GB), Apple M-series (up to 128 GB+), Ryzen AI Max (128 GB) — gpt-oss-20b, Qwen 3 mid-sizes, quantized 70B-class models.

What it's for

The high-volume, low-stakes lane: bulk refactors, test generation, commit messages, embeddings, doc drafts, log triage — the tokens that dominate agent volume.

Why it matters

Marginal cost ≈ electricity. Works offline and on planes. Sensitive code never leaves the machine. Latency is a bus ride, not a round trip.

Local isn't a toy tier — it's where agents burn their cheapest tokens, and the proof that the stack survives with the network cable pulled.

Eyes open

What we gain — and what it honestly costs.

Gains

  • Irrevocable capability — weights on our storage can't be repriced, retired, or embargoed.
  • Fixed-cost inference — agent volume stops being a budget event.
  • Hard data boundary — prompts never leave the tenant or the desk.
  • No shared rate limits — burst capacity is ours to schedule.
  • Multipolar sourcing — US, CN, and EU model families in one portfolio.

Costs

  • Operations — serving stacks need tuning and upgrades. Mitigation: Foundry runs the platform; we run policy and evals.
  • Frontier gap — the hardest reasoning still favors closed leaders. Mitigation: the escape-valve lane routes the hardest ~5% out, by policy.
  • Commitment risk — reserved GPUs only pay off when utilized. Mitigation: start serverless; reserve only on observed utilization data.
  • Eval burden — model swaps need regression gates, not vibes. Mitigation: eval suite in CI is phase-one work, not an afterthought.
  • License & provenance review — per checkpoint, before adoption. Mitigation: a standing review gate; favored set is MIT/Apache.

How we start

A 90-day path from pilot to policy.

Days 0–30 · Prove

Stand it up

  • Pick two token-heavy workloads (agentic coding, doc/RAG pipeline).
  • Deploy the gateway; wire Foundry serverless DeepSeek/Qwen + local Ollama.
  • Baseline evals and per-lane cost telemetry from day one.

Days 31–60 · Route

Move the bulk lane

  • Route bulk agentic traffic to open lanes behind eval gates in CI.
  • Deploy one managed-compute endpoint; harden VNet + Private Link.
  • Measure utilization to size any GPU reservation honestly.

Days 61–90 · Scale

Make it policy

  • Onboard remaining teams; tune batching, caching, quantization.
  • Publish the cost & sovereignty scorecard vs. the frontier baseline.
  • Set the standing routing policy and the reserve-vs-serverless mix.
